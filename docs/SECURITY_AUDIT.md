# Аудит информационной безопасности панели УООЗД

Версия 1.0 · 13.10.2026 · Объект: `reestr_server.py` v14 + `демо.py` + «Модуль извещения»

Оценка по шкале: 🔴 критично · 🟠 высокое · 🟡 среднее · 🔵 низкое.

## 1. Что уже сделано хорошо (не ломать при переработке)

1. **Пароли — только хэши.** PBKDF2-HMAC-SHA256 со случайной солью 16 байт, сравнение через `hmac.compare_digest` (устойчиво к тайминг-атакам) — строки 4218–4259.
2. **Сессии — случайные токены** `secrets.token_urlsafe(24)`, cookie с `HttpOnly; SameSite=Lax`, срок жизни ограничен (30 дней) — строки 4263–4287, 7937.
3. **Атомарная запись файлов** (`write_atomic`) — реестр не портится при падении посреди записи.
4. **Защита от обхода пути** в отдаче файлов: `root not in f.parents` — проверяется, что запрошенный файл внутри разрешённой папки (строка 7904).
5. **Разграничение ролей**: удаление — только у назначенных (`can_delete`), реестры отделов — по принадлежности (`oz_can`, `ovrk_can`).
6. **Ограничение размера запроса** — 30 МБ (строка 7829).
7. В демо отсутствуют `eval`, `exec`, `pickle`, `os.system`, `subprocess` по пользовательским данным — проверено поиском по коду.

## 2. Найденные проблемы

### 🔴 1. Нет TLS — трафик, пароли и cookie идут открытым текстом
Сервер — `ThreadingHTTPServer` по HTTP на `0.0.0.0:8090` (строка 8462). В корпоративной сети пароль можно перехватить пассивным сниффером.
**Мера:** запускать за reverse-proxy (nginx/IIS) с TLS и сертификатом домена; либо обернуть сокет в `ssl.SSLContext`. После включения HTTPS добавить cookie-флаг `Secure` (сейчас его нет — см. строку 7937) и заголовок `Strict-Transport-Security`.

### 🔴 2. Демо-режим входа (`ВХОД_ПО_ПАРОЛЮ = False`) доверяет заголовку `X-Demo-As`
`current_user()` берёт логин прямо из заголовка запроса (строка 7815): любой в сети может представиться администратором одним HTTP-заголовком.
**Мера:** флаг `ВХОД_ПО_ПАРОЛЮ` должен быть `True` в боевой конфигурации; добавить в `main()` отказ запуска с `ВХОД_ПО_ПАРОЛЮ=False` вне localhost, либо явное предупреждение при старте. **Исправлено в патче** (`patch_reestr_server.py` / уже внесено в рабочую копию — вход по логину и паролю включён).

### 🟠 3. Слабая защита от перебора пароля
Единственная мера — `time.sleep(1)` после неудачи (строка 7930). Нет блокировки учётной записи и ограничения по IP: ботнет перебирает со многих адресов, пауза не мешает.
**Мера:** реализовано в `modules/auth_mysql.py` — счётчик неудач, блокировка 15 минут после 5 попыток, таблица `login_attempts`, алерт в журнал. Минимальный патч для текущего файлового режима также внесён в рабочую копию (блокировка по IP+логину).

### 🟠 4. Минимальная длина пароля — 6 знаков (строка 4312)
Не соответствует парольной политике организаций здравоохранения (обычно 8–12 с проверкой на словарь).
**Мера:** в новом модуле — минимум 10 знаков, запрет пароля = логину, проверка по списку типовых (`password_policy()` в `auth_mysql.py`).

### 🟠 5. Нет заголовков безопасности HTTP
Ответы отдаются без `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`. Панель можно встроить в чужой iframe (clickjacking), а внедрённый через данные скрипт выполнится без ограничений.
**Мера:** внесено в рабочую копию — единая функция `security_headers()` добавляет `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, базовую CSP `default-src 'self' 'unsafe-inline'` (инлайн-стили/скрипты — особенность текущего PANEL_HTML; ужесточение CSP с nonce — следующий шаг).

### 🟡 6. Текст исключения уходит клиенту
`fail()` отправляет `f'Ошибка на сервере: {e}'` (строка 8270): внутренние пути, имена полей и фрагменты SQL/файловой структуры попадают в браузер.
**Мера:** клиенту — нейтральное «Внутренняя ошибка, № …», подробности — только в журнал. Заложено в новый HTTP-слой.

### 🟡 7. Сессии и хэши в JSON-файлах рядом с приложением
`Панель — сессии.json` и файл пользователей лежат в `ПАПКА_ПАНЕЛИ` на сетевом диске, доступном отделу. Токен сессии в файле — в открытом виде: скопировав файл, входят под любым пользователем.
**Мера:** в MySQL — `sessions.token_hash` = SHA-256 от токена (сам токен не хранится); файловый режим — права NTFS «только служба панели», папка вне общего доступа.

### 🟡 8. Итераций PBKDF2 меньше рекомендуемых
120 000 (строка 4219). OWASP (2023+) рекомендует для PBKDF2-HMAC-SHA256 от 210 000.
**Мера:** `auth_mysql.py` — 210 000, число итераций хранится в `users.hash_iters` и повышается прозрачно при следующем входе пользователя.

### 🟡 9. XML/архивы — риск XXE и «zip-бомб» при будущем импорте
Текущий код XML не парсит; при добавлении импорта XML типовая ошибка — `xml.etree`/`lxml` с включёнными внешними сущностями.
**Мера:** `modules/xml_import.py` отклоняет документы с `<!DOCTYPE`, `<!ENTITY`, `xinclude` ещё до парсинга; лимит размера файла 20 МБ и глубины вложенности.

### 🔵 10. Нет аудита неудачных входов и выхода сессий «везде»
В журнал пишется только успешный вход (строка 7941). **Мера:** `login_attempts` + запись в `audit_log` вида `kind='auth'`; администратор видит подбор пароля.

### 🔵 11. CSRF
Формы — JSON POST из того же origin; `SameSite=Lax` закрывает базовый сценарий. При появлении кросс-доменных интеграций — добавить `X-CSRF-Token` (двойная отправка cookie).

### 🔵 12. Секреты в конфиге в открытом виде
`МАКС_ТОКЕН`, `ПОЧТА_ПАРОЛЬ` — константы в коде (строки 82–88). **Мера:** переменные окружения / Windows Credential Manager; `config.ini` с правами 600, вне веб-корня и системы контроля версий.

## 3. Требования к целевому решению (чек-лист внедрения)

| # | Требование | Где реализовано |
|---|---|---|
| 1 | TLS на всём пути, `Secure`+`HttpOnly`+`SameSite=Lax` у cookie | reverse-proxy + патч cookie |
| 2 | Вход по логину/паролю обязателен; демо-режим только на localhost | патч в рабочей копии |
| 3 | PBKDF2 ≥ 210 000 итераций, соль 16 байт, `compare_digest` | `modules/auth_mysql.py` |
| 4 | Пароль ≥ 10 знаков, не равен логину, не из топ-списка; смена при первом входе (`must_change`) | `password_policy()` |
| 5 | Блокировка 15 мин после 5 неудач; журнал попыток | `auth_mysql.py` + `login_attempts` |
| 6 | Сессии: в БД — хэш токена, отзыв (`revoked`), срок 12 ч для боевого режима | `sessions` |
| 7 | Права в БД: приложению — только его БД, без DELETE на журналы | `schema.sql` (комментарий) |
| 8 | Заголовки безопасности на всех ответах | внесено в рабочую копию |
| 9 | XML только без DTD/ENTITY, лимиты размера | `modules/xml_import.py` |
| 10 | Клиенту — нейтральные ошибки, стек — в журнал | целевой HTTP-слой |
| 11 | Резервное копирование БД ежедневно, проверка восстановления ежемесячно | эксплуатация |
| 12 | Обновления MySQL и библиотек по расписанию; `pip-audit` в CI | эксплуатация |

## 4. Остаточный риск

После внедрения пп. 1–10 основные остаточные риски — целевая компрометация учётки администратора (смягчается блокировкой и аудитом) и доступ к сетевому диску с файлами документов (смягчается правами NTFS и хэшами `sha256` в БД, которые покажут подмену файла).
