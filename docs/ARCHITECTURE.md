# Архитектура панели УООЗД с хранением в MySQL

Версия 1.0 · 13.10.2026

## 1. Что меняется и зачем

Сейчас панель (`reestr_server.py`, ~16 000 строк) хранит всё в файлах:

| Данные | Сейчас | Проблема |
|---|---|---|
| Реестры ОАО | `Реестр <год>.xlsx` | один файл на год, конфликты при одновременной работе, нужна блокировка «файл открыт в Excel» |
| ОПАиЗ (заявки, СЗ, счета, договоры ЕП, КП) | JSON в `Панель\` | нет транзакций, размер растёт, поиск полным перебором |
| ОВРК (договоры, УПД, платёжки, ДС, претензии) | JSON в `Панель\` | то же |
| Пользователи и сессии | JSON в `Панель\` | файл с хэшами лежит рядом с приложением |
| Журнал, новости, уведомления | JSON | нет индексов, выборки — чтение файла целиком |

Целевая схема: **MySQL 8.0+ как единственное хранилище данных**, файлы (docx/pdf/xlsx платёжки) — как сейчас, на сетевом диске, в БД — только пути и контрольные суммы.

## 2. Слои

```
┌─────────────────────────────────────────────────────┐
│ Браузер (PANEL_HTML, без изменений по верстке)      │
├─────────────────────────────────────────────────────┤
│ HTTP-слой   Handler (do_GET/do_POST)                │
│             аутентификация → modules/auth_mysql.py  │
│             авторизация по отделам/ролям            │
├─────────────────────────────────────────────────────┤
│ Сервисный слой  submit_from_panel, handle_apply,    │
│             oz_*, ovrk_*, izv_* — логика без смены  │
│             публичных функций                       │
├─────────────────────────────────────────────────────┤
│ Слой доступа  modules/db.py — пул соединений,       │
│             репозитории: RegistryRepo, OzRepo,      │
│             OvrkRepo, UsersRepo, JournalRepo …      │
├─────────────────────────────────────────────────────┤
│ MySQL 8.0  InnoDB · utf8mb4 · транзакции · FK       │
└─────────────────────────────────────────────────────┘
     импорт: Excel (как раньше) + XML (modules/xml_import.py)
```

Принципы:

1. **Код панели меняется только в точках чтения/записи.** Все `load_workbook(...)`, `_json_file(...)`, `write_atomic(...)` для данных заменяются вызовами репозиториев с теми же сигнатурами ответов. Экраны и API не трогаем — фронтенд не заметит переезда.
2. **Одна запись — один раз.** Папки «входящие» обрабатывает watcher; импорт (Excel или XML) сначала пишется в `import_batch`, потом маппится на таблицы. Дубль по уникальному ключу → отказ или «на проверке», как сейчас.
3. **Журнал — append-only.** Таблица `audit_log` заменяет `Реестр — журнал.json`; писать можно только добавлением.
4. **Файлы — вне БД.** В БД храним относительный путь, имя, sha256, дату получения. Это даёт контроль целостности платёжек и договоров.
5. **Excel остаётся форматом выгрузки** («Реестр .xlsx», «Excel» в таблицах) — генерируется из БД тем же кодом openpyxl.

## 3. Схема БД

Полный DDL — в `schema.sql`. Ключевые сущности:

- `users`, `sessions`, `login_attempts` — вход и защита от перебора (см. раздел ИБ);
- `employees`, `departments`, `counterparties` — справочники;
- `procurements` — строки реестра ОАО (конкурентные и неконкурентные, все годы одной таблицей, поле `year`);
- `protocols`, `protocol_participants` — протоколы и участники;
- `contracts` — договоры (связь с закупкой и с ОВРК);
- `ovrk_documents`, `ovrk_payments`, `contract_addenda`, `claims` — исполнение (ОВРК);
- `oz_*` — реестры ОПАиЗ (заявки, СЗ 1С, запросы КП, договоры ЕП, счета, ДС, позиции СЗ);
- `news`, `notifications`, `audit_log` — журналы;
- `import_batches`, `import_items` — что загружено из файлов (Excel/XML), статус разбора;
- `kb_articles` — статьи базы знаний (редактируются из панели, при первом запуске заполняются из `knowledge_base/`).

Год — это поле, а не файл: переключатель «2025 · 2026 · 2027» становится `WHERE year = ?`, аналитика «по годам» — один запрос вместо чтения трёх книг Excel.

## 4. План миграции (без остановки работы)

| Этап | Содержание | Результат |
|---|---|---|
| 1 | Поставить MySQL 8.0, создать БД `uoozd`, применить `schema.sql`, пользователь `uoozd_app` только с правами на эту БД | пустая БД |
| 2 | `pip install pymysql cryptography` ; `modules/migrate_excel_to_mysql.py --dry-run`, затем без флага | данные из Excel/JSON — в БД, панель ещё работает по-старому |
| 3 | Переключить репозитории: `config.ini → storage: mysql` | панель читает/пишет MySQL; Excel-реестры становятся «только выгрузка» |
| 4 | Параллельная эксплуатация 2 недели, сверка контрольных сумм строк | уверенность, что ничего не потерялось |
| 5 | Отключить запись в Excel; папки «входящие» продолжают работать через `import_batches` | файловый режим — архив |

Откат на любом этапе до 5 — вернуть `storage: files`, Excel-файлы не удалялись.

## 5. Конфигурация подключения

Никаких паролей в коде. `config.ini` (права 600, вне веб-корня):

```ini
[storage]
backend = mysql            ; files — старый режим

[mysql]
host = 10.0.0.10
port = 3306
database = uoozd
user = uoozd_app
; пароль — из переменной окружения UOOZD_DB_PASSWORD или Windows Credential Manager
ssl_ca = C:\certs\ca.pem   ; соединение с БД — по TLS
```

## 6. Производительность

- Индексы в `schema.sql` покрывают все экранные фильтры (номер ОАО, год, ответственный, ИНН, статус, даты).
- `/api/data` сейчас перечитывает Excel целиком при каждом опросе (каждые 10 с у всех открытых вкладок). С БД — `SELECT` по индексам + `ETag` по `MAX(updated_at)` → 304 без тела, нагрузка падает на порядки.
- Журнал — `SELECT ... WHERE id > ?` вместо чтения всего JSON.

## 7. Что НЕ переносится в БД

- Сами docx/pdf/xlsx/txt (платёжки, извещения, договоры) — сетевой диск, как сейчас;
- кэш распознавания — пересчитывается;
- временные файлы экспорта.

## 8. Связанные документы

- `schema.sql` — DDL;

- `knowledge_base/Форматы файлов.md` — форматы данных (то же — в разделе «База знаний» самой панели).
